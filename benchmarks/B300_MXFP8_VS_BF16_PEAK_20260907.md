# B300 MXFP8 vs BF16 GEMM 峰值对照（BF16 API 输入/输出）

## 结论

在同一张 Modal `NVIDIA B300 SXM6 AC`、同一批 shape、同一组 BF16
源输入上：

- 随机 `uniform[-1, 1]` 输入的实测峰值为 **MXFP8 2838.04 TFLOPS**、
  **BF16 1456.38 TFLOPS**，独立峰值比为 **1.949x**。在共同的
  `16384^3` shape 上是 **1.966x**。
- 全 1 低切换功耗控制组在 `32768^3` 达到 **MXFP8 4564.11 TFLOPS**、
  **BF16 2281.94 TFLOPS**，比值为 **2.000x**，与 B300 的 2:1 标称
  dense Tensor Core 比例一致。

这里的“输入输出都是 BF16”指 API 边界：`X`、`W` 的源张量与 `Y` 都是
BF16。MXFP8 Tensor Core 真正读取的乘法操作数必然是由 BF16 动态量化得到的
E4M3 值和 E8M0 block scales。本报告只讨论 `mxfp8_core`：量化在计时区外，
TFLOPS 只由 MXFP8 GEMM 的 CUDA Event 时间计算，不计 BF16 -> MXFP8
转换成本。

## 全部结果

### 随机 BF16 输入

| shape | BF16 core TFLOPS | MXFP8 core TFLOPS | MXFP8 / BF16 |
|---:|---:|---:|---:|
| 4096^3 | 1328.25 | 2375.99 | 1.789x |
| 8192^3 | **1456.38** | 2801.81 | 1.924x |
| 16384^3 | 1443.53 | **2838.04** | **1.966x** |
| 32768^3 | 1422.72 | 2642.19 | 1.857x |

### 全 1 BF16 输入（低切换功耗控制组）

| shape | BF16 core TFLOPS | MXFP8 core TFLOPS | MXFP8 / BF16 |
|---:|---:|---:|---:|
| 4096^3 | 1827.10 | 3368.73 | 1.844x |
| 8192^3 | 2222.70 | 4285.17 | 1.928x |
| 16384^3 | 2238.08 | 4472.89 | 1.999x |
| 32768^3 | **2281.94** | **4564.11** | **2.000x** |

## 为什么随机输入的 `32768^3` 低于 `16384^3`

随机输入的原始 core 数据如下：

| 方法 / shape | 单发延迟 | TFLOPS | 平均功耗 | 平均 SM 时钟 | software power cap active |
|---|---:|---:|---:|---:|---:|
| BF16 `16384^3` | 6.093 ms | 1443.53 | 1059.0 W | 1232 MHz | 100% |
| BF16 `32768^3` | 49.461 ms | 1422.72 | 1086.9 W | 1192 MHz | 100% |
| MXFP8 `16384^3` | 3.099 ms | 2838.04 | 1043.7 W | 1203 MHz | 100% |
| MXFP8 `32768^3` | 26.633 ms | 2642.19 | 1093.1 W | 1114 MHz | 100% |

每个 repeat 连续执行 20 发，因此 MXFP8 的计时块由 `16384^3` 的约 62 ms
增长到 `32768^3` 的约 533 ms。更长的随机数据计算持续贴住 1100 W 功耗墙，
GPU 将 SM 时钟从约 1203 MHz 降到 1114 MHz（下降 7.4%）；同期 MXFP8
吞吐从 2838.04 降到 2642.19 TFLOPS（下降 6.9%）。BF16 也出现方向一致但
幅度更小的时钟和吞吐下降。

全 1 控制组排除了“shape 变大天然导致效率下降”这个解释：`16384^3` 与
`32768^3` 的 MXFP8 SM 时钟都约为 2032 MHz，吞吐反而从 4472.89 上升到
4564.11 TFLOPS；BF16 也从 2238.08 上升到 2281.94 TFLOPS。因此当前证据
指向的主因是随机数据下的稳态功耗限频，而不是 Tensor Core tile 利用率。

本次脚本没有记录 cuBLASLt heuristic algorithm ID 或实际 kernel name，所以
不能严格排除 `16384^3` 与 `32768^3` 选择不同实现带来的次要影响；但
“时钟下降 7.4% / 吞吐下降 6.9%”以及全 1 对照都表明功耗墙是主导因素。

## 正确性

独立 `1024^3` 随机输入用 FP32 GEMM 作参考：

| 路径 | 输出 | relative L2 vs FP32 | all finite |
|---|---|---:|---|
| BF16 | BF16 | 0.1660% | PASS |
| MXFP8 core | BF16 | 3.3607% | PASS |

这里验证的是计算链路与预期量化误差，不表示 MXFP8 具有 BF16 数值精度；
MXFP8 路径虽然源输入和输出是 BF16，计时区内的乘法输入已经量化为
E4M3/E8M0。
